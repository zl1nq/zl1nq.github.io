缓存基础

目的：减轻数据库压力、提升接口响应速度。

热点数据类型：商品信息、首页数据、用户基础信息、字典数据。

缓存流程：请求先查 Redis → 命中直接返回；未命中再查 MySQL，查到后写入 Redis → 返回。

缓存穿透

定义：请求不存在的键，导致数据库压力增加，影响性能。

解决方法：

  1. 设置一个空值，防止再次穿透
  2. 使用布隆过滤器，防止穿透

缓存雪崩

定义：大量缓存 key 同时过期失效，大量请求直接打到数据库，造成数据库压力骤增甚至宕机。

解决方法

1. 过期时间增加随机值（最简单、首选）

不要统一设置相同过期时长。

作用：打散过期时间，避免大批量 key 同一时刻失效。

2. 缓存永不过期（逻辑过期）

不给 key 设置 TTL，不主动删除。额外保存一个「逻辑过期时间」在 value 内部。

流程：

  1. 查询缓存
  2. 判断是否逻辑过期
  3. 未过期 → 直接返回
  4. 已过期 → 返回旧数据，异步开启线程去更新缓存

✅ 优点：不会出现大规模同时失效
❌ 缺点：会短暂返回旧数据，存在数据不一致

3. Redis 集群高可用架构

防止 Redis 宕机导致整体雪崩。

  • 主从 + 哨兵 / Redis Cluster 集群
  • 避免单点 Redis 故障，所有缓存全部不可用

4. 服务层限流 + 熔断 + 降级

即使缓存全部失效，也要保护数据库：

  • 限流：限制到达 DB 的请求数量
  • 熔断：数据库压力过高时直接熔断
  • 降级：返回兜底默认数据，不再访问数据库

常用组件：Sentinel、Resilience4j

5. 多级缓存

本地缓存（Caffeine、Guava Cache）+ Redis 分布式缓存。

请求顺序：本地缓存 → Redis → DB

即使 Redis 大面积失效，本地缓存依然可以扛一部分流量。

6. 定时主动刷新热点缓存

对于核心热点数据，不等待过期被动加载；后台定时任务主动更新 Redis，不让它走到过期。

缓存击穿

定义：热点单一 key 过期，大量请求直接打到数据库，导致数据库压力骤增，影响性能。

方案 1：互斥锁（分布式锁）

思路：热点 key 失效时，只放行一个请求去查数据库、更新缓存；其他请求等待重试。

流程：

  1. 查询 Redis，数据不存在
  2. 尝试获取分布式锁
  3. 获取成功 → 查询 DB，写入 Redis，释放锁
  4. 获取失败 → 短暂休眠后重试读取缓存

实现：SET lock NX EX / Redisson

✅ 优点：数据一致性较好
❌ 缺点：有等待、存在死锁风险，并发高时有性能损耗

方案 2：逻辑过期（热点数据首选）

不给 key 设置 TTL，缓存永不主动失效；在 value 里存入逻辑过期时间。

流程：

  1. 获取缓存，判断是否逻辑过期
  2. 未过期：直接返回
  3. 已过期：立刻返回旧数据，同时异步开启线程更新缓存

✅ 优点：无等待、吞吐量高，适合允许短暂不一致的热点场景
❌ 缺点：会短暂返回旧数据，存在数据不一致

更新策略

核心问题：数据库和缓存数据如何同步，解决数据一致性问题。

先更新数据库，再删除缓存（业界首选）

流程：

  1. 更新 MySQL
  2. 删除 Redis 缓存（不是更新缓存）

✅ 优点：

  • 绝大多数场景一致性最好；
  • 不用频繁更新缓存，减少无效写；

❌ 极端问题：并发脏读问题

线程 A 更新 DB，还没删缓存；线程 B 查询，命中旧缓存，读到脏数据。持续时间极短，业务大多可接受。

优化方案：删除缓存时加延迟双删。

延迟双删流程：

  1. 更新数据库
  2. 删除缓存
  3. 休眠一小段时间（几百 ms）
  4. 再次删除缓存

原理：等待正在执行的查询请求完成，如果期间有请求把旧数据重新写入缓存，第二次删除把脏缓存清掉。
