一、synchronized 体系：wait/notify

注意：这三个方法是 Object 的成员方法，不是 Thread 的方法；依赖 synchronized 监视器锁（Monitor）。

1. 前提铁律

  1. 调用 obj.wait() / obj.notify() 的线程，必须先持有 obj 的监视器锁
    • 写在 synchronized(obj) 内部
    • 如果没有持有锁，直接抛出：IllegalMonitorStateException
  2. 轻量级锁、偏向锁状态下调用 wait()
    • JVM 会直接把锁膨胀为重量级锁
    • 因为 wait 需要 Monitor 内部的 WaitSet 等待队列，前两种锁没有 Monitor

2. 方法清单

方法 作用
wait() 释放锁，进入 WaitSet 无限等待，直到被唤醒
wait(long timeout) 限时等待，超时自动唤醒
notify() 随机唤醒 WaitSet 中一个等待线程
notifyAll() 唤醒 WaitSet 全部等待线程

wait() 核心三步

  1. 立即释放当前持有的 obj 监视器锁（重点！sleep 不会释放锁）
  2. 当前线程进入该对象的 WaitSet 等待队列，阻塞休眠
  3. 被唤醒后不会立刻执行，需要重新竞争锁；抢到锁之后，才从 wait 方法返回继续运行

notify() vs notifyAll()

  • notify()：随机唤醒一条；容易出现信号丢失、线程永久休眠，生产尽量少用
  • notifyAll()：唤醒全部，避免线程饿死，推荐优先使用

⚠️ 经典坑：notify 只是把线程从 WaitSet 移到 EntryList，不代表立刻运行；仍然需要重新抢到锁才能从 wait 返回。

3. 完整执行流程

  1. 线程 A 拿到 obj 的重量级锁
  2. 执行 obj.wait()
    • 释放 Monitor 的 _owner 锁
    • 当前线程移入 WaitSet 队列阻塞
  3. 线程 B 抢到锁，执行 obj.notify()
    • 将一条线程从 WaitSet 移动到 _EntryList
  4. 线程 A 被移入 EntryList 后，仍然需要竞争锁，拿到锁之后才从 wait 返回继续执行

4. 时序示例

执行顺序：

  1. A 获取锁 → 执行 wait → 释放锁，进入等待队列
  2. B 获取锁，执行 notify
  3. A 被移入 EntryList，开始和其他线程竞争锁
  4. A 再次抢到锁，从 wait 返回

5. 虚假唤醒：必须用 while，不能用 if

原因：虚假唤醒（Spurious Wakeup）

操作系统可以在没有 notify 的情况下，无故唤醒 WaitSet 中的线程。
如果用 if，唤醒后不再检查条件直接往下走，业务逻辑出错；
while 唤醒后再次校验条件，不满足继续等待。

经典原则：永远用 while 包裹 wait()，不要用 if。

6. wait() vs sleep()

对比项 wait() sleep()
归属 Object 方法 Thread 静态方法
锁行为 释放监视器锁 不释放任何锁
唤醒方式 notify/notifyAll、超时 时间结束、interrupt 中断
使用位置 synchronized 内部 任意位置

7. 常见易错点汇总

  1. wait 释放锁，唤醒后要重新竞争锁；
  2. notify 只是转移线程队列，不立刻运行线程；
  3. wait/notify 必须在 synchronized 块，锁对象必须是同一个 obj；
  4. 调用 wait 触发锁膨胀成重量级锁；
  5. 不要混用锁对象：synchronized(A){ B.wait() } → 直接报错；
  6. 不要在循环外写 wait，永远搭配 while 判断业务条件。

二、Lock 体系：Condition 条件队列

Condition 是 java.util.concurrent.locks 下的接口，配合 Lock（AQS） 使用，用来实现等待/唤醒，对标 Object.wait()/notify()，但能力更强。

最核心差距：

  • 一条 Lock 可以创建多个独立 Condition；
  • synchronized 的监视器仅有唯一一条 WaitSet 等待队列。

1. 核心方法

2. 相比 Object.wait 的巨大优势

一把锁可以创建多个独立 Condition 队列

生产满了只唤醒消费者，不用唤醒生产者，减少无效竞争。

3. 使用模板

4. 底层结构（AQS 视角）

AQS 存在两类队列，完全隔离：

  1. 同步队列（双向 CLH 队列）
    • 抢锁失败的线程存放于此；竞争锁的主队列。
  2. Condition 条件队列（单向链表）
    • 调用 await() 的线程进入这里。
    • 节点状态：CONDITION，标记当前节点在条件队列。

5. 完整流转过程

  1. 线程调用 lock.lock()，成功持有锁；
  2. 执行 condition.await()
    • 创建/复用 AQS Node，状态设为 CONDITION，加入条件队列尾部；
    • 释放当前持有的锁；
    • 线程 park() 阻塞等待。
  3. 其他线程拿到锁，执行 condition.signal()
    • 将条件队列头部节点移出；
    • 把节点转移到 AQS 同步队列；
    • 解除阻塞，等待竞争锁。
  4. 线程抢到锁之后，从 await() 方法返回，继续执行业务。

重点区分：
await 被 signal 唤醒 ≠ 拿到锁，仍然要去同步队列竞争锁，和 wait 逻辑一致。

6. 关键规则

  1. 调用 await()/signal() 必须先获取 Lock 锁
    没有持有锁调用，直接抛出 IllegalMonitorStateException，和 wait 要求一致。
  2. 同样存在虚假唤醒！必须 while 循环判断条件
  3. signal() vs signalAll()
    • signal()：转移条件队列第一个节点到同步队列；
    • signalAll()：把条件队列所有节点全部迁移到同步队列。

三、AQS 同步队列（CLH 双向队列）

AQS（AbstractQueuedSynchronizer）内部两大队列：

  1. 同步队列（Sync Queue，双向 CLH 队列）：抢锁失败的线程排队竞争锁；
  2. Condition 条件队列（Condition Queue，单向链表）：await() 等待业务条件的线程。

两者相互独立，节点会在两个队列之间迁移。

1. 同步队列结构

  • 数据结构：双向链表
  • 节点类型：static final class Node
  • 核心成员：
    • prev：前驱节点
    • next：后继节点
    • thread：封装的线程
    • waitStatus：节点状态（核心）
  • 存在虚头结点（head）：head 节点不关联任何有效线程，仅作为哨兵；真正排队线程从 head.next 开始。

2. Node.waitStatus 五种状态

状态 值 含义
SIGNAL -1 后继线程需要被唤醒；当前节点释放锁后，要唤醒下一个
CANCELLED 1 线程取消等待（中断/超时），废弃节点，不再参与竞争
CONDITION -2 当前节点在【Condition 条件队列】，不在同步队列
PROPAGATE -3 共享锁模式下，唤醒向后传播
初始状态 0 默认状态

3. 独占模式下同步队列完整流程（ReentrantLock）

抢锁成功

state=0，CAS 修改 state=1，设置 exclusiveOwnerThread=当前线程，不进入同步队列。

抢锁失败

  1. 把当前线程封装成 Node；
  2. 从尾部追加到同步双向队列；
  3. 自旋检查：只有前驱是 head，才有资格尝试抢锁；
  4. 抢不到，将前驱节点状态改为 SIGNAL，然后调用 LockSupport.park() 阻塞。

为什么要看前驱节点？ CLH 队列思想：每个节点只负责唤醒后继。

释放锁（unlock）

  1. state 自减；重入锁需要减到 0 才算完全释放；
  2. 清空独占线程 owner；
  3. 找到 head 后继有效节点，LockSupport.unpark() 唤醒线程；
  4. 被唤醒的线程再次 CAS 竞争 state。

⚠️ 关键点：唤醒 ≠ 拿到锁，依旧存在竞争（非公平锁尤为明显）。

4. 同步队列 ↔ Condition 条件队列 节点流转（高频考点）

  1. 线程持有锁，调用 condition.await()
    • 当前 Node 从同步队列移出；
    • 修改 waitStatus = CONDITION；
    • 追加进入条件队列（单向链表）尾部；
    • 释放 AQS 锁，线程 park 阻塞。
  2. 其他线程执行 condition.signal()
    • 将条件队列头部节点取出；
    • 清除 CONDITION 标记；
    • 把该节点移入同步队列尾部；
    • 此时线程还没运行，等待竞争锁。

核心记忆：

  • await：同步队列 → 条件队列
  • signal：条件队列 → 同步队列

节点只要带有 CONDITION，就代表它不在同步队列，无法参与锁竞争。

5. 同步队列 VS synchronized 的 EntryList

很多人混淆，区分开：

  • synchronized Monitor：_EntryList（等待抢锁队列）、_WaitSet（等待唤醒队列）
  • AQS：同步队列（对应 EntryList）、Condition 条件队列（对应 WaitSet）

逻辑模型相似，但实现完全不同：
Monitor 由 JVM C++ 实现；AQS 纯 Java 代码实现双向 CLH 链表。

6. 公平锁与非公平锁

类型 行为 特点
非公平锁（默认） 新线程上来直接 CAS 抢 state；抢不到才入同步队列 新线程可以插队，队列里的线程可能饥饿；吞吐量高
公平锁 新线程先检查同步队列是否有等待节点；如果有人排队，直接进入队列尾部 绝不插队，先来先得；吞吐量稍低

四、LockSupport 底层阻塞工具

java.util.concurrent.locks.LockSupport

底层阻塞工具类，AQS、Condition、Lock 全部依赖它实现线程阻塞与唤醒。
它是 wait/await 的底层基石。

1. 核心两个原生操作

2. park/unpark 原理（二元许可机制）

操作系统层面理解：每个线程有一张 “许可 (permit)”

  • permit 只有两种状态：可用、不可用，最多一张，不能累积。

park()：

  • permit = 可用：立刻消耗许可，线程继续运行，不阻塞
  • permit = 不可用：线程阻塞等待许可

unpark(thread)：

  • 给目标线程发放一张 permit
  • 如果线程正在 park 阻塞，直接唤醒；
  • 如果线程还没调用 park，先存入许可；后续调用 park 会直接放行，不会阻塞。

⭐ 关键特性：unpark 可以先于 park 执行！

这是和 notify/wait 最大区别。
notify 如果提前执行，信号直接丢失，后续 wait 永久阻塞。

4. 支持中断

  1. 线程在 park() 阻塞时，调用 thread.interrupt()
    → 线程被唤醒；不会抛出 InterruptedException
  2. 需要代码手动检测中断标记 Thread.currentThread().isInterrupted()

和 sleep/wait/await 不一样：park 被中断不会抛异常。

5. park 的重载

6. LockSupport VS wait/notify

特性 LockSupport park/unpark Object wait/notify
依赖锁 不需要持有任何锁 必须持有监视器锁
信号时序 unpark 可以先执行，许可保留 notify 先执行，信号丢失
粒度 精确唤醒指定线程 随机唤醒一个 / 全部
中断响应 唤醒，不抛异常 唤醒，抛出 InterruptedException
底层 Unsafe API，操作系统线程原语 JVM Monitor

8. 经典误区

误区 1：unpark 可以多次调用累积许可

✅ permit 最多 1 张；连续多次 unpark，效果等价一次。

误区 2：park 解除阻塞只有 unpark 一种方式

三种场景 park 会返回：

  • 其他线程调用 unpark(当前线程)
  • 当前线程被 interrupt() 中断
  • park 限时版本到达超时时间
