Java并发编程02：synchronized & volatile

Synchronized 关键字

1、基本概念

  • synchronized 是 Java 内置的互斥锁，也叫对象锁或内置锁。
  • 保证原子性：同一时刻只有一个线程能执行被 synchronized 保护的代码。
  • 保证可见性：线程解锁时，会将共享变量刷新到主内存；加锁时，会从主内存重新读取。
  • 保证有序性：通过互斥执行，消除指令重排序带来的问题。

核心作用：解决多线程并发访问共享资源时的线程安全问题。

4、核心特性

  • 可重入性：同一个线程可以多次获得同一把锁，不会自己锁死自己。
  • 排他性：同一时刻只能有一个线程持有锁（悲观锁）。
  • 自动释放：线程执行完同步代码或发生异常时，会自动释放锁。
  • 锁的是对象而非方法：关键看锁的是哪个对象。

5、底层原理

对象头（Object Header）

Java 对象在内存中分为三部分：

  1. 对象头：存储对象的元数据，包括 Mark Word、类指针等。
  2. 实例数据：对象的成员变量。
  3. 对齐填充：保证对象大小是 8 字节的倍数。

Mark Word 是 synchronized 实现锁的关键，它存储了锁的状态信息：

锁状态 Mark Word 内容
无锁 对象哈希码 + 分代年龄
偏向锁 偏向线程 ID + Epoch + 分代年龄
轻量级锁 指向栈中锁记录的指针
重量级锁 指向 Monitor 对象的指针

Monitor 对象

当锁升级为重量级锁时，JVM 会为对象分配一个 Monitor（管程）对象：

  • Entry Set：等待获取锁的线程队列。
  • Owner：当前持有锁的线程。
  • Wait Set：调用 wait() 等待的线程队列。

6、锁升级过程

锁状态是单向不可逆膨胀

  • 偏向锁、轻量级锁完全不用 Monitor、不依赖操作系统内核阻塞，全程靠 CAS + MarkWord + 线程栈帧在用户态实现互斥；
  • Monitor 只是重量级锁的”阻塞队列管理器”，前三级锁不靠它也能保证同一时间只有一个线程执行同步代码；
  • 互斥本质：通过 CAS 修改 MarkWord，抢占标记所有权，抢占失败就自旋重试（轻量级）或直接排队膨胀重量级锁。

CAS 是什么

  • Compare and Swap（比较并交换）是一种原子操作，用于在多线程环境下更新共享变量。
  • 它通过将当前值与预期值进行比较，如果相等则更新为新值，否则保持当前值不变。
  • 该操作是原子的，确保了线程安全。

Compare And Swap：比较内存当前值和预期值，相等才修改，原子操作（CPU 硬件指令保证）。所有偏向/轻量级锁的互斥根基就是 CAS。

6.1 偏向锁

  • 适用于单线程重复获取锁的场景。
  • 第一次获取锁时，记录线程 ID，后续同一线程直接获取，无需 CAS 操作。

场景：始终只有 A 线程访问同步块

  • 对象初始是无锁，MarkWord 标记位 01（无锁/偏向模式），偏向线程 ID=0；
  • A 线程第一次进入 synchronized(obj)：用 CAS 把 MarkWord 里的线程 ID 改成自己，同时开启偏向标记；
  • 后续 A 线程再次进入同步代码：直接读取 MarkWord，发现里面存的线程 ID = 当前线程，不用任何 CAS，直接获取锁；
  • 互斥保证：MarkWord 里记录了唯一持有线程，别的线程进来 CAS 修改线程 ID 会失败，触发偏向撤销升级轻量级锁。

没有其他线程时，全程偏向锁，MarkWord 永久记录 A 线程 ID，不会出现多线程同时进入同步块。

出现竞争的互斥逻辑：

此时新开线程 B 抢锁：B 执行 CAS 修改 MarkWord 的线程 ID，CAS 失败 → JVM 发起偏向撤销，暂停 A 线程，清空 MarkWord 线程 ID，升级轻量级锁。

6.2 轻量级锁

  • 当有多个线程交替获取锁时，偏向锁升级为轻量级锁。
  • 使用 CAS 操作尝试获取锁，失败则自旋等待。

流程（两个线程交替执行，不并发争抢）：

  1. 线程 A 进入同步块：在自己的虚拟机栈创建一块空间 Lock Record（锁记录），存储 MarkWord 的拷贝（displaced mark word）；用 CAS 把对象 MarkWord 改成「指向 A 栈锁记录的指针」。CAS 成功 → A 持有轻量级锁。
  2. A 没释放锁时，线程 B 来抢：B 同样创建锁记录，执行 CAS 尝试修改 MarkWord 指针 → CAS 失败；B 进入自旋循环：不断重试 CAS 抢锁（用户态，不切换内核、不用 Monitor）。
  3. A 执行完同步代码：通过 CAS 把对象 MarkWord 恢复成原来的拷贝，释放锁；B 自旋 CAS 成功，持有锁执行。

互斥关键点：同一时刻，MarkWord 只能存储一个栈锁记录的地址，CAS 原子操作保证只有一个线程修改成功；失败线程自旋等待，不会出现两个线程同时进入同步代码。

关于 Lock Record：

  1. 保存对象原始的 Mark Word（Displaced Mark Word）：轻量级锁加锁前，对象头里存着无锁/偏向锁信息。线程先把这份原始数据拷贝到自己栈帧的 Lock Record 里。等同步代码执行完毕、释放锁时，再用 CAS 把 Lock Record 里保存的旧 MarkWord 写回对象头，完成解锁。如果没有 Lock Record，原始锁状态会丢失，没法恢复对象到无锁状态。
  2. 作为”持有锁凭证”，实现互斥与可重入：对象 Mark Word 里会存指向当前线程 Lock Record 的指针，代表锁被这条线程占有。其他线程 CAS 修改 MarkWord 必然失败，触发自旋；同一线程多次进入同步块（锁重入），会在线程栈新增多条 Lock Record，解锁时一一出栈匹配，保证重入次数对应，不会提前释放锁。

6.3 重量级锁

  • 当自旋次数过多或线程阻塞时，升级为重量级锁。
  • 涉及操作系统内核态切换，性能开销较大。
触发时机

轻量级锁大量自旋抢锁失败，JVM 判定竞争激烈，锁单向膨胀为重量级锁；只有到这一步，对象才会真正创建 Monitor 监视器。

底层核心结构：ObjectMonitor（监视器）

每个膨胀后的对象绑定一个 Monitor，关键属性：

  • _owner：记录当前持有锁的线程，null = 无线程占用
  • _EntryList：抢锁失败、阻塞等待锁的线程队列（没拿到锁，排队等）
  • _WaitSet：调用 wait() 释放锁后，等待唤醒的线程队列

底层依托操作系统内核互斥量 mutex，线程阻塞会交给 OS 调度。

MarkWord 变化：膨胀后对象头 MarkWord 不再存线程 ID/LockRecord 指针，而是直接存 Monitor 的内存地址。

重量级锁完整执行流程

  1. 线程执行 monitorenter 尝试抢占 _owner：

    • 如果 _owner 为空：当前线程持有锁，_owner = 当前线程；
    • 如果 _owner 被别的线程占用：线程不再自旋，进入 _EntryList，操作系统将该线程阻塞挂起，让出 CPU；

  2. 持有锁线程执行同步代码，执行完毕执行 monitorexit：

    • 清空 _owner；
    • OS 唤醒 _EntryList 里等待的线程，重新竞争锁；

  3. 若线程在同步块内调用 obj.wait()：

    • 释放 _owner 锁；
    • 当前线程移入 _WaitSet 休眠；

  4. 调用 notify() / notifyAll()：

    • 从 WaitSet 取出一条/全部线程，移回 EntryList 重新抢锁。
核心特征（对比偏向/轻量级锁）
  • 进入内核态，开销巨大：自旋是用户态循环；重量级锁阻塞、唤醒线程需要操作系统切换上下文，保存寄存器、栈现场，切换成本高。
  • 不再自旋，不浪费 CPU：竞争激烈场景下，不会空循环占用 CPU，适合大量线程同时争抢。
  • 依赖 Monitor，支持 wait/notify：偏向、轻量级锁没有等待队列，无法实现等待唤醒机制；只有重量级锁才能用 wait()。
  • 非公平锁：新到来的线程可以直接竞争锁，不需要排队，可能导致队列里的线程长期拿不到锁（线程饥饿）。
  • 支持可重入：Monitor 内部记录锁重入次数，多次加锁需要对应次数解锁才会释放。
什么时候一定会膨胀为重量级锁？
  • 多线程同一时刻疯狂争抢锁，轻量级锁自适应自旋多次全部失败；
  • 同步代码内调用 wait()，会直接膨胀成重量级锁（必须依靠 WaitSet 队列）。

7、常见误区

  • 锁的是对象不是代码：两个方法如果锁的不是同一个对象，依然存在并发问题。
  • 字符串常量池陷阱：synchronized ("abc") 可能导致不同代码段意外地互相阻塞。
  • 死锁：两个线程互相持有对方需要的锁，导致永久阻塞。

8、极简面试背诵版

  • synchronized 是 Java 内置互斥锁，保证原子性、可见性、有序性；
  • 三种用法：修饰实例方法（锁 this）、静态方法（锁 Class）、代码块（锁指定对象）；
  • 锁可重入、自动释放、排他性；
  • 底层依赖对象头 Mark Word 和 Monitor；
  • 锁升级过程：无锁→偏向锁→轻量级锁→重量级锁。

Volatile 关键字

volatile 的作用：

  1. 确保多线程之间的可见性，防止缓存优化导致的可见性问题。
  2. 禁止指令重排序，确保程序执行顺序。

1、可见性问题

底层原理：CPU 有各级缓存，每个线程有自己的工作内存缓存变量副本。

  • 不加 volatile：主线程修改变量写入主存时机不确定，其他线程看不到最新值；
  • 加 volatile：写操作后强制刷新到主存；读操作强制从主存读取，不使用本地缓存。

2、指令重排序

指令重排序：CPU/JVM 为提高执行效率，会在不影响单线程结果的前提下，调换代码执行顺序。

经典使用场景：双重检查锁 DCL 单例

不加 volatile 会出现空指针问题：

new 对象的三步操作

instance = new Singleton() 这行代码底层拆成 3 个独立指令：

  1. 分配内存空间：分配一块堆内存，大小足够存 Singleton 对象；
  2. 初始化对象：执行构造方法，初始化对象成员变量；
  3. 赋值引用：把引用变量 instance 指向刚分配的内存地址。

无 volatile 时的问题

指令重排可能导致执行顺序变为 1→3→2：分配内存 → 赋值引用 → 初始化对象。

并发场景复现：

  1. 线程 A 进入同步块，执行 instance = new Singleton()，CPU 重排先走 1、3；
  2. instance 已经有地址（此时 instance 不再是 null）；
  3. CPU 切换线程，A 暂停，对象还没执行初始化步骤；
  4. 线程 B 进入外层判断 if (instance == null)，发现 instance 不为 null，直接返回；

出问题🤯：线程 B 拿着一个内存分配成功、但构造函数没走完、成员变量全是默认零值的残缺对象去使用。

volatile 如何解决🧐

volatile 会在赋值操作前后插入 StoreLoad 内存屏障，硬性禁止初始化（步骤 2）跑到引用赋值（步骤 3）后面，强制执行顺序永远 1→2→3。

只有对象完全初始化完毕，才会把地址赋值给 instance，其他线程拿到的一定是完整可用对象。

3、内存屏障（Memory Barrier）完整讲解

核心前提：CPU、JVM 会做指令重排序优化，重排分四类，有四种对应屏障禁止对应重排。

设两条操作：Load = 读变量、Store = 写变量

四种重排类型：

  • Load1 → Load2（读读重排）
  • Load1 → Store2（读写重排）
  • Store1 → Load2（写读重排）
  • Store1 → Store2（写写重排）

四种内存屏障分别阻止上面某一类重排，volatile 底层就是靠这四类屏障实现可见性 + 有序性。

四种基础内存屏障

1. StoreStore 写-写屏障

作用：屏障前所有写操作，一定先于屏障后的写操作，禁止 Store1 重排到 Store2 后面。

保证：Store1 数据刷新缓存完毕，才执行 Store2 写入。

2. LoadLoad 读-读屏障

作用：屏障前所有读操作，一定先于屏障后的读操作，禁止 Load1 重排到 Load2 后面。

保证：先读完 Load1 主存最新数据，再去读 Load2。

3. LoadStore 读-写屏障

作用：屏障前读，屏障后写；禁止前面 Load 重排到后面 Store 之后。

哪怕 CPU 想把 Store2 提前执行，屏障强制 Load1 先完成。

4. StoreLoad 写-读屏障（代价最大，volatile 核心屏障）

作用：屏障前所有写操作全部刷新到主存；屏障后所有读操作强制从主存读取。禁止 Store1 重排到 Load2 后面。

特点：开销最高，会同步缓存、清空本地缓存；volatile 写后面必然插入 StoreLoad 屏障，解决 DCL 单例重排问题靠的就是它。
