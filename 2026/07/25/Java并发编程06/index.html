为什么要用线程池

  1. 降低资源消耗：复用线程，避免频繁创建销毁线程的系统开销
  2. 提高响应速度：任务到达时无需新建线程，直接执行
  3. 方便管控：限制最大并发数、任务排队、拒绝策略、监控线程状态

⚠️ 不使用线程池的风险：大量创建 new Thread() → OOM、频繁 GC、CPU 暴涨

核心类：ThreadPoolExecutor

构造方法 7 个核心参数🤯

参数详解

1. corePoolSize 核心线程

  • 默认一直存活，不会被回收（开启 allowCoreThreadTimeOut 才会超时回收）
  • 任务提交时，核心线程未满 → 新建核心线程执行任务

2. maximumPoolSize 最大线程数

最大线程数 = 核心线程数 + 非核心线程数

  • 非核心线程空闲超过 keepAliveTime 会被回收

3. workQueue 阻塞队列（存放等待任务）

常用队列：

队列 特点
ArrayBlockingQueue 有界队列，基于数组
LinkedBlockingQueue 无界 / 有界；无界时任务无限堆积，永远不会创建非核心线程
SynchronousQueue 不存储元素，直接提交任务，必须有空闲线程接收
DelayQueue 延迟任务队列

4. 拒绝策略 handler

触发时机：队列满、线程达到 maximumPoolSize 时。

内置 4 种策略：

策略 行为
AbortPolicy（默认） 直接抛出 RejectedExecutionException
CallerRunsPolicy 让提交任务的主线程执行任务
DiscardPolicy 静默丢弃当前任务，不抛异常
DiscardOldestPolicy 丢弃队列最老任务，尝试加入新任务

💡 生产建议：自定义拒绝策略，记录日志、告警，不要直接使用默认抛异常。

任务提交执行流程

  1. 提交任务 execute()
  2. 核心线程数 < corePoolSize → 创建核心线程执行任务
  3. 核心线程已满 → 任务放入阻塞队列
  4. 队列已满 → 创建非核心线程执行任务
  5. 线程总数达到 maximumPoolSize → 触发拒绝策略

四种常见线程池

为什么禁止？

✅ 推荐：手动 new ThreadPoolExecutor，明确参数。

线程池状态（5 种）

状态 说明
RUNNING 正常运行，接收任务
SHUTDOWN 调用 shutdown()，不接收新任务，执行队列剩余任务
STOP 调用 shutdownNow()，中断运行任务，丢弃队列任务
TIDYING 所有任务结束，线程数 0，准备执行 terminated() 钩子
TERMINATED 终止完成

核心问题

1. 如何合理设置线程池参数？

分场景：

  • CPU 密集型任务：核心线程 ≈ CPU 核心数 + 1
  • IO 密集型任务（数据库、网络请求）：设置更大，一般 2 * CPU核心数 ~ CPU核心数 / (1 - 阻塞系数)

💡 生产最佳实践：通过压测动态调整，不要写死；配合监控观察队列堆积、活跃线程数。

2. execute() 和 submit() 区别

对比项 execute() submit()
入参 只接收 Runnable 支持 Runnable / Callable
返回值 无 返回 Future
异常处理 异常直接抛出 异常保存在 Future，调用 get() 才抛出

3. 核心线程什么时候创建？

  • 默认懒创建：任务提交时才新建，不会线程池初始化就创建
  • 可调用 prestartAllCoreThreads() 提前启动所有核心线程

4. 如何处理线程池内任务异常

  • execute：异常直接打印，线程结束，线程池会新建线程补充
  • submit：异常存在 Future，不调用 get() 看不到异常

解决方案：任务内部 try-catch 或自定义 ThreadFactory 包装线程、重写 afterExecute 钩子

面试背诵版

  1. 为什么用线程池：降低资源消耗、提高响应速度、方便管控（限流、排队、监控）。
  2. 7 大核心参数：corePoolSize、maximumPoolSize、keepAliveTime、unit、workQueue、threadFactory、handler。
  3. 执行流程：核心线程 → 队列 → 非核心线程 → 拒绝策略；使用无界队列时 maximumPoolSize 失效。
  4. 4 种拒绝策略：AbortPolicy（抛异常）、CallerRunsPolicy（调用者执行）、DiscardPolicy（丢弃）、DiscardOldestPolicy（丢最老的）。
  5. Executors 为什么不推荐：底层用无界队列或无限最大线程数，高并发下 OOM 风险大。
  6. 5 种状态：RUNNING → SHUTDOWN → STOP → TIDYING → TERMINATED。
  7. 参数设置：CPU 密集型设为核心数+1；IO 密集型设更大；生产靠压测+监控调优。
  8. execute vs submit：execute 只接 Runnable 无返回、异常直接抛；submit 有 Future 返回、异常存 Future 里。
