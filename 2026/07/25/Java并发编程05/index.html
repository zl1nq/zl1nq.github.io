一、什么是阻塞队列

BlockingQueue 位于 java.util.concurrent 包，继承自 Queue 接口，是线程安全的队列。

⭐ 核心价值：在并发场景下，自动处理线程的阻塞与唤醒，开发者无需手动写 wait/notify 逻辑。

1. 两大阻塞特性

场景 行为
队列满时 往队列添加元素的线程阻塞，直到队列有空位
队列空时 从队列获取元素的线程阻塞，直到队列有数据

2. 核心规则

  • ❌ 不允许 null 元素，插入 null 直接抛出 NullPointerException
  • ✅ 线程安全：所有操作都是原子的、线程安全的
  • 🎯 典型场景：生产者 - 消费者模型

1. 抛出异常组

队列满/空时直接抛出异常，不推荐在并发场景使用。

方法 异常场景 异常类型
add(e) 队列满时调用 IllegalStateException
remove() 队列空时调用 NoSuchElementException
element() 队列空时调用 NoSuchElementException

2. 返回特殊值组（非阻塞）

立即返回结果，不会阻塞线程，适合尝试性操作。

方法 成功返回 失败返回
offer(e) true false（队列满）
poll() 队首元素 null（队列空）
peek() 队首元素 null（队列空）

3. 阻塞等待组（生产者消费者最常用）⭐

队列不满足条件时，线程无限阻塞，直到条件满足或被中断。

方法 行为
put(e) 队列满，线程无限阻塞，直到有空位 / 线程中断
take() 队列空，线程无限阻塞，直到有元素 / 线程中断

💡 开发建议：实现生产者消费者模型，首选 put() / take() 组合。

4. 超时等待组（限时等待）

阻塞一段时间，超时后返回失败，不会无限等待。

方法 说明
offer(e, long timeout, TimeUnit unit) 等待指定时长，放不进去返回 false
poll(long timeout, TimeUnit unit) 等待指定时长，取不到返回 null

⚠️ 重要提醒：阻塞方法（put/take/超时版本）被线程 interrupt() 中断时，会抛出 InterruptedException，必须捕获处理。

三、六大实现类详解

1. ArrayBlockingQueue

基于数组的有界阻塞队列

核心特点：

  • 📦 有界队列：初始化必须指定容量，后续不能扩容
  • 🔒 一把锁：使用一把 ReentrantLock，生产者、消费者共用同一把锁，无法并发读写
  • 📊 FIFO：先进先出
  • ⚖️ 公平锁可选：开启后等待线程按顺序获取资源，吞吐量略低

2. LinkedBlockingQueue

基于单向链表，可选有界 / 无界阻塞队列

核心特点：

  • ⚠️ 默认无界：不指定容量时，最大为 Integer.MAX_VALUE，无限添加会造成 OOM
  • 🔐 两把锁：putLock（入队锁）、takeLock（出队锁）
  • ✅ 高并发：生产者和消费者可以并发执行，并发性能优于 ArrayBlockingQueue
  • 📊 FIFO：先进先出
  • 🧵 线程池应用：Executors.newFixedThreadPool() 底层使用该队列

3. PriorityBlockingQueue

支持优先级的无界阻塞队列

核心特点：

  • 📈 无界队列：内部数组自动扩容
  • 🏆 优先级排序：元素必须实现 Comparable 接口，或者构造时传入 Comparator
  • ❓ 同优先级无序：不保证同优先级元素的顺序
  • 🔀 非 FIFO：获取元素按优先级排序，不是先进先出
  • ➡️ 只有出队阻塞：队列永远不会满，put() 永远不会阻塞

4. DelayQueue

延时无界阻塞队列

存放实现 Delayed 接口的对象，元素到期之后才能被取出。

适用场景：

  • ⏰ 定时任务调度
  • 📦 订单超时自动取消
  • 🗑️ 缓存过期清理

核心特点：

  • take() 只会获取已经过期的元素
  • 元素未到期时，线程阻塞等待
  • 底层基于 PriorityQueue 实现，按过期时间排序

5. SynchronousQueue

不存储元素的阻塞队列，容量 = 0

核心机制：put 和 take 必须配对

  • 生产者 put 之后阻塞，直到有消费者 take
  • 消费者 take 之后阻塞，直到有生产者 put
  • 没有内部缓冲区，相当于线程之间直接传递任务

典型应用：

  • Executors.newCachedThreadPool() 底层使用它

6. LinkedTransferQueue（较少使用）

TransferQueue 子接口，无界链表队列

新增 transfer() 方法：

生产者尝试直接转交元素给消费者，没有消费者则阻塞；性能较强。

四、实现类横向对比

实现类 是否有界 数据结构 锁机制 特点 典型场景
ArrayBlockingQueue ✅ 有界 数组 一把锁 初始化必须指定容量，不可扩容，并发一般 固定容量的任务队列
LinkedBlockingQueue ⚠️ 可选 单向链表 两把锁（读写分离） 默认无界，并发性能好，注意 OOM 风险 线程池任务队列
PriorityBlockingQueue ❌ 无界 数组（堆） 一把锁 按优先级出队，非 FIFO 优先级任务调度
DelayQueue ❌ 无界 优先级队列 一把锁 按延迟时间出队，元素需实现 Delayed 定时任务、缓存过期
SynchronousQueue ✅ 容量为0 无（直接传递） CAS + 锁 不存储元素，直接交接 缓存线程池
LinkedTransferQueue ❌ 无界 链表 CAS transfer 直接转交，性能强 高并发消息传递

💡 选型建议：

  • 大多数场景用 ArrayBlockingQueue 或 LinkedBlockingQueue
  • 需要排序用 PriorityBlockingQueue
  • 需要延迟用 DelayQueue
  • 直接传递任务用 SynchronousQueue

五、生产者消费者模型

阻塞队列最经典的应用就是生产者消费者模式。

代码示例

执行流程说明

  1. 生产者生产 5 个商品，队列容量为 3
  2. 生产到第 4 个时，队列满，生产者阻塞
  3. 消费者消费商品后，队列有空位，生产者被唤醒继续生产
  4. 整个过程无需手动写 wait/notify，BlockingQueue 自动处理

✅ 优势：

  • 解耦：生产者和消费者互不依赖
  • 削峰：队列缓冲，防止消费者被打垮
  • 简单：无需手动维护线程同步

六、底层原理

⭐ 核心总纲：所有阻塞队列底层都依托 AQS → ReentrantLock + Condition 实现线程阻塞与唤醒；
不同实现类（数组 / 链表 / 优先级）只是存储结构不同，阻塞机制的核心思想完全一致。

下面以面试最高频的 ArrayBlockingQueue 源码为例讲解，再对比 LinkedBlockingQueue。

1. 核心基础：Lock + Condition

Condition 是显式锁的等待队列，等价于 synchronized 的 wait/notify，但功能更强：
一把锁可以创建多个独立的等待条件（生产者等待队列、消费者等待队列相互隔离）。

Condition 作用 谁等待 谁唤醒
notEmpty 队列空时，消费者等待 消费者 await() 生产者 signal()
notFull 队列满时，生产者等待 生产者 await() 消费者 signal()

💡 对比 synchronized：
wait() / notify() 只能有一个等待集合，所有线程混在一起，容易产生虚假唤醒；
Condition 可以精准分类等待线程，唤醒更高效。

2. await() / signal() 工作流程

condition.await()

  1. 当前线程释放持有的锁
  2. 线程进入 Condition 的等待队列，阻塞休眠（LockSupport.park()）
  3. 被唤醒后，重新竞争锁，拿到锁之后才从 await() 返回，继续执行后续代码

condition.signal()

  1. 从条件等待队列取出头部一个线程节点
  2. 把该节点移入 AQS 同步队列（锁的等待队列）
  3. 线程在同步队列中等待竞争锁，被调度到后才真正执行

⚠️ 重要规则：await() 和 signal() 必须在持有锁时调用，否则直接抛出 IllegalMonitorStateException，和 wait/notify 规则一致。

  2. while 判断队列是否空 → 防虚假唤醒
  3. 空则 notEmpty.await() → 释放锁，消费者阻塞
  4. 有元素则出队 → 环形数组操作
  5. notFull.signal() → 唤醒等待的生产者

4. LinkedBlockingQueue 双锁机制

LinkedBlockingQueue 用两把锁实现更高并发：

为什么两把锁并发更高？

操作 ArrayBlockingQueue（一把锁） LinkedBlockingQueue（两把锁）
入队 + 出队 互斥，不能同时进行 ✅ 可以并发执行
入队 + 入队 互斥 互斥（同一把 putLock）
出队 + 出队 互斥 互斥（同一把 takeLock）

💡 双锁的代价：代码复杂度更高，需要同时操作两把锁时（如 remove(Object)）要按顺序加锁，防止死锁。

5. 底层机制总结

阻塞队列的线程安全和阻塞唤醒，最终都落到 AQS 和 LockSupport 上。

七、常见问题与注意事项

1. 为什么不允许 null 元素？

因为 poll() 等方法用 null 作为特殊返回值表示队列空。
如果允许存 null，就无法区分「取出的元素是 null」还是「队列空」。

2. ArrayBlockingQueue vs LinkedBlockingQueue 怎么选？

对比项 ArrayBlockingQueue LinkedBlockingQueue
容量 必须指定，有界 可选，默认无界
数据结构 数组 链表
锁 一把锁（读写共用） 两把锁（读写分离）
并发性能 一般 较高
内存占用 预分配，固定 动态创建节点，按需分配
GC 压力 低（无节点创建回收） 高（频繁创建回收节点）

选择建议：

  • 容量固定、追求低 GC → ArrayBlockingQueue
  • 高并发、不确定容量 → LinkedBlockingQueue（记得设上限，防 OOM）

3. 阻塞队列如何保证线程安全？

  • 入队、出队操作都有锁保护（ReentrantLock）
  • 队列满/空时，通过 Condition 实现线程的等待与唤醒
  • 类似 AQS 的 Condition.await() / signal() 机制

4. 常见使用陷阱

陷阱 说明
⚠️ LinkedBlockingQueue 默认无界 不指定容量会导致 OOM，一定要设容量
⚠️ 阻塞方法不处理中断 put/take 会抛 InterruptedException，必须捕获
⚠️ 误用 add/remove 并发下抛异常影响业务，优先用 put/take
⚠️ PriorityBlockingQueue 元素不可比较 元素必须实现 Comparable 或传 Comparator

八、面试背诵版

  1. 阻塞队列是什么：BlockingQueue 是线程安全的队列，队列满时入队阻塞，队列空时出队阻塞，常用于生产者消费者模型。

  2. 四组核心方法：

    • 抛出异常：add / remove / element
    • 返回特殊值：offer / poll / peek
    • 阻塞等待：put / take
    • 超时等待：offer(timeout) / poll(timeout)

  3. 六大实现类：

    • ArrayBlockingQueue：数组有界，一把锁
    • LinkedBlockingQueue：链表可选有界，两把锁并发高
    • PriorityBlockingQueue：优先级无界，非 FIFO
    • DelayQueue：延迟无界，元素到期才能取
    • SynchronousQueue：容量为 0，直接交接
    • LinkedTransferQueue：transfer 直接转交

  4. Array vs Linked：Array 有界固定容量、一把锁、低 GC；Linked 可选无界、两把锁、并发高但注意 OOM。

  5. 底层原理：

    • 核心 = ReentrantLock + Condition（依托 AQS）
    • ArrayBlockingQueue：一把锁 + 两个 Condition（notEmpty、notFull）
    • LinkedBlockingQueue：两把锁（putLock + takeLock），读写分离并发高
    • put 满了 await notFull，入队后 signal notEmpty
    • take 空了 await notEmpty，出队后 signal notFull

  6. await/signal 流程：

    • await：释放锁 → 进条件队列阻塞 → 被唤醒后重新抢锁
    • signal：条件队列头节点 → 移入 AQS 同步队列 → 等待抢锁

  7. 经典应用：线程池的任务队列、生产者消费者模式、消息队列、限流削峰。

  8. 为什么不允许 null：因为 poll/peek 用 null 表示队列空，存 null 会导致语义混淆。
