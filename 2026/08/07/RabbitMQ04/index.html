一、交换机总览：消息的分拣中心

⭐ 一句话理解：Exchange（交换机）= RabbitMQ 消息的分拣中心。生产者不直接投队列，而是先发给交换机，由它根据规则决定消息发给哪些队列。

1. 消息流转模型（含交换机）

角色 职责
Publisher 生产者：发送消息到 Exchange，不再发到队列
Exchange 交换机：接收消息，根据类型 + RoutingKey 路由到对应队列
Queue 队列：存储消息，必须与交换机绑定（Binding）
Consumer 消费者：订阅队列，无变化

2. ⚠️ 交换机不存消息！

核心认知：Exchange 只负责转发消息，没有存储能力。

如果没有任何队列与 Exchange 绑定，或者没有符合路由规则的队列 → 消息直接丢失！

（队列才是真正存储消息的地方）

3. 四种交换机类型

类型 中文名 路由规则 使用频率
Fanout 广播 / 扇出 发给所有绑定的队列，忽略 RoutingKey ⭐⭐⭐
Direct 精确路由 / 订阅 RoutingKey 必须与绑定的 BindingKey 完全相等 ⭐⭐⭐⭐⭐
Topic 通配符订阅 RoutingKey 匹配通配符 BindingKey（* / #） ⭐⭐⭐⭐
Headers 头匹配 基于消息 Header 匹配，性能差 极少用

💡 本章节重点讲解前三种（Fanout/Direct/Topic），Headers 日常开发基本不用。

二、Fanout 交换机：广播模式

📢 Fanout = 广播：不管消息的 RoutingKey 是什么，把消息转发给所有绑定到本交换机的队列。

1. 路由规则

Fanout 的 5 个要点：

  1. 可以有多个队列
  2. 每个队列都要绑定到 Fanout Exchange
  3. 生产者发消息 → 交换机
  4. 交换机把消息复制 N 份发给每个绑定队列
  5. 订阅各队列的消费者都能拿到完整消息

三、Direct 交换机：精确路由模式

🎯 Direct = 精确匹配：队列绑定 Exchange 时指定一个或多个 BindingKey，消息的 RoutingKey 必须完全相等，才转发给该队列。

1. 路由规则

Fanout 是「不管什么消息全部队列都发一份」，但实际业务中我们常常需要：

  • 红色消息 → 只给 Q1 和 Q2
  • 蓝色消息 → 只给 Q2 和 Q3

Direct 模式就能做到精确控制。

2. 关键概念区分

术语 谁设置的 作用
RoutingKey 生产者 发消息时携带 消息的「地址标签」
BindingKey 队列 和 交换机绑定时约定 队列的「收件规则」
匹配逻辑 —— RoutingKey 完全等于 BindingKey → 才转发

5. 特殊情况：多个队列同 BindingKey

如果多个队列绑定了同一个 BindingKey，Direct 的行为就等价于 Fanout——所有匹配队列都会收到一份消息。

四、Topic 交换机：通配符模式

🌐 Topic = Direct 的升级版：允许 BindingKey 使用通配符，RoutingKey 仍为普通多单词格式（. 分隔）。

相比 Direct 更灵活：比如要做「所有商品相关的消息都发过去」，用 Topic 一个 item.# 就能覆盖，不用列几十个 BindingKey。

1. 通配符规则

BindingKey 一般由多个单词 + . 分隔组成，例如：item.insert、china.news。

通配符 含义
#（井号） 匹配 0 个、1 个或多个词
*（星号） 匹配不多不少恰好 1 个词

2. 匹配示例

BindingKey 能匹配的 RoutingKey（打 ✅，不能 ❌）
item.# ✅ item.spu.insert、✅ item.spu、✅ item（0 个也可以
item.* ✅ item.spu、❌ item.spu.insert（多了1个词不行、❌ item（没词不行

五、三种交换机对比选型

维度 Fanout（广播） Direct（精确） Topic（通配符）
路由逻辑 忽略 RoutingKey，所有绑定队列都收 RoutingKey 完全等于 BindingKey 才发 RoutingKey 匹配通配符 BindingKey
BindingKey 形式 任意（被忽略，无需 RoutingKey） 普通字符串，比如 red 多单词 + 通配符 * / #
灵活性 ❌ 最差（全广播） ⭐⭐⭐ 中（绑定什么发什么） ✅ 最强（通配符，模糊匹配）
同一条消息可达队列数 所有绑定队列（N份） 所有 BindingKey 等于 RoutingKey 的队列 通配符匹配到的队列（0~N）
典型场景 系统广播、公告通知 精确分类路由（red/blue 不同颜色分开） 分层业务（商品、订单等多业务分类）

🧠 选型建议：

  • 要全广播 → Fanout
  • 要精确分类、路由简单 → Direct
  • 要灵活路由、业务有层级结构 → Topic
  • 能用 Direct 的场景一般别用 Fanout（精准投递，避免无用消息浪费
