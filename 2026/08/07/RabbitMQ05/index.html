一、为什么需要声明式

⭐ 声明式 = 幂等保证：在程序启动时，把「我要用的队列、交换机、绑定关系及它们的属性」告诉 RabbitMQ，如果不存在就自动创建；如果已存在且属性一致，则什么也不做（幂等）。

1. 手动控制台创建的痛点

痛点 说明
跨团队交接容易出错 程序员写代码定义了 10 个队列，交给运维在控制台手动创建，漏一个就报错
环境重复劳动 dev、test、prod 三套环境，每套都要手动在控制台创建一遍
属性不一致隐患 控制台手选的 durable / exclusive / autoDelete 属性与程序员预期不一致，运行时出诡异问题

2. 声明式的优势

💡 本质：把「在控制台手点鼠标创建」改为「代码声明自动创建」，从手工流程变成程序自动化流程。

二、声明式总览：两种实现方式

Spring AMQP 提供了两种主流声明方式，最终效果完全等价（都会在启动时发 AMQP 的 declare 命令），只是写法和适用场景不同：

方式 写法 核心类/注解 适用场景
方式一：@Bean + 配置类 写 @Configuration 类，用 @Bean 返回 Queue / Exchange / Binding 对象 ExchangeBuilder QueueBuilder BindingBuilder 需要在无消费者的公共模块 / 多工程共用队列时
方式二：@RabbitListener 注解 在监听方法上用 @QueueBinding 声明 @RabbitListener + @QueueBinding + @Queue + @Exchange 有消费者时最常用，把监听+声明写在一起

🧠 两种方式可以混用：比如公共模块用方式一预先建基础队列，业务模块的消费者用方式二声明自己的专属队列。

四、方式二：基于 @RabbitListener 注解

⭐ 生产环境最常用：把监听方法和声明绑定写在一起，省掉单独的 @Configuration 类。

五、核心参数详解（重要）

🧠 这些参数直接影响数据安全和行为，不管用哪种声明方式都必须理解！

1. 交换机与队列共通参数

参数 可选值 默认值 含义
durable true / false true（大部分 Builder 默认） 持久化：RabbitMQ 重启后，这个交换机/队列还在不在？true=重启仍在，false=重启丢失
autoDelete true / false false 自动删除：当最后一个消费者断开连接后，自动删除该队列/交换机

2. Queue 独有的重要参数

参数 可选值 默认值 含义
exclusive true / false false 排他队列：仅声明它的同一个连接可见；连接关闭（不管 durable 是什么）自动删除。常见于临时应答队列
deadLetterExchange 交换机名 无 死信交换机：队列里消息过期或被 NACK 时，路由到这个交换机再处理（死信队列 DLQ 机制）
maxLength 数字 无 队列最大消息数，超过时按 overflow 策略处理
messageTTL 毫秒数 无 队列中消息的默认过期时间，超过自动丢弃或进死信

3. durable / exclusive / autoDelete 组合理解

🌰 场景化理解：

组合 典型用途
durable=true, exclusive=false, autoDelete=false 业务核心队列：重启不丢、多消费者共用、不自动删
durable=false, exclusive=true, autoDelete=true 临时 RPC 应答队列：用完即扔，连接断开就删

六、两种方式对比选型

维度 @Bean + @Configuration @RabbitListener + @QueueBinding
代码组织 集中在配置类里，统一管理 分散在各消费者监听方法旁边
消费者依赖 不需要有消费者，纯声明也能生效 必须配合消费者监听
复杂属性配置 Builder 链式，类型安全、方便写 arguments 注解写 arguments 略繁琐（要写 @Argument type）
公共模块场景 ✅ 适合：比如 common 模块提前建共享队列 ❌ 不合适：公共模块没消费者
业务开发场景 略啰嗦，要写好几个 Bean ✅ 最简洁：监听+声明一体
新手上手难度 Bean 依赖注入容易搞混（bind时引用方法） 注解一站式，简单直观

🧠 选型建议：

  • 业务开发，有消费者 → 优先方式二（@QueueBinding），代码最少最清爽
  • 公共模块建共享队列、死信交换机等高级配置 → 方式一（@Bean），更灵活
  • 两者可以共存不冲突

七、常见坑与注意事项

坑 1：属性不一致导致启动失败 ❌

⚠️ 幂等的前提是属性一致。

如果控制台里已经建了一个 simple.queue，设置的是 durable=false；而代码里声明为 durable=true → 属性冲突 → 应用启动直接抛异常 IOException: channel error; PRECONDITION_FAILED！

解决：要么删了队列让代码重建，要么代码声明和控制台保持完全一致。

坑 2：忘记加 @Component / @Configuration ❌

  • 方式一的 @Configuration 类必须能被 Spring 扫描到（在启动类子包下）
  • 方式二的 @RabbitListener 所在类必须加 @Component 交给 Spring 管理
  • 不加的话声明和监听都完全不生效，且没有明显报错，调试很坑

坑 3：@Bean 绑定方法直接调用 Bean 方法 ❓

✅ 安全的：Spring 的 @Configuration 类是 CGLIB 代理的，同一个配置类内调用其他 @Bean 方法不会重复创建对象，而是从容器拿单例。但如果换别的配置类调用，要用参数注入 @Autowired Queue fanoutQueue1 再传。

坑 4：默认 durable 不设置 ❌

new Queue("xxx") 默认 durable=true（和 RabbitMQ 协议一致），但 QueueBuilder 的 durable() 明确写了更清晰，推荐用 Builder 方式把重要参数写出来，方便阅读。
