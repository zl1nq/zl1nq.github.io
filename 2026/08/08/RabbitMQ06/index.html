一、消息转换器的作用与流程

⭐ 消息转换器 = 「Java 对象 ⇄ 字节数组」的翻译官，因为 RabbitMQ Broker 只认 bytes，传输层不能直接存 Java 对象。

1. 发送与接收的完整流转

2. Spring AMQP 默认 MessageConverter

Spring AMQP 中 RabbitTemplate 和 @RabbitListener 都依赖 MessageConverter 接口，其默认实现是：

默认实现类 序列化方式 说明
SimpleMessageConverter JDK 原生序列化 对于 String 传文本、byte[] 原样传、其他 Object 一律走 JDK ObjectOutputStream

🧠 为什么需要自定义？ 默认 JDK 序列化问题太多（见下章），生产 99% 场景都要替换成 JSON 序列化方案。

二、默认转换器：JDK 序列化的三大问题

⚠️ JDK 序列化 = 默认但不可用：三个核心缺陷决定了它只适合 demo，绝对不能上生产。

问题 严重程度 具体说明
📦 数据体积过大 🟡 中 JDK 序列化不仅写数据本身，还要写整个类的全限定名、字段描述符、继承链、序列化版本号 UID 等元信息，一般比 JSON 大 3~10 倍，浪费 Broker 磁盘和网络带宽
🛡️ 有安全漏洞 🔴 高危 反序列化时自动执行 readObject() 恶意 payload，经典 Java 反序列化漏洞（CVE 系列），一旦 Broker 被投毒消息，消费者反序列化即 RCE 远程执行命令
👓 可读性差 🟡 中 控制台看到的是乱码字节（\xAC\xED\x00\x05 开头的 JDK 魔数），排障时没法直接看内容，调试体验极差

🌰 直观对比：发送一个 {name: "Jack", age: 21} 的 Map：

  • JDK 序列化：约 300+ 字节乱码，控制台完全不可读
  • JSON 序列化：约 30 字节的 {"name":"Jack","age":21}，清晰可读

六、核心机制详解：TypeId 与 MessageId

🧠 这两个是使用 JSON 转换器时最容易被忽略、但出问题最难排查的「幕后机制」。

1. __TypeId__：反序列化的「导航地图」

机制流程

示例对照表

发送的 Java 对象 消息头 TypeId 写的值 消费者反序列化成
new HashMap() java.util.HashMap HashMap
com.example.pojo.User com.example.pojo.User User 类
List<User>（通过 TypeReference） java.util.ArrayList ArrayList（内部元素按 User 字段还原为 LinkedHashMap，这是另一个坑）

2. 跨服务时的 TypeId 陷阱 ❓

⚠️ 问题：A 服务包名是 com.order.pojo.OrderDTO，B 服务包名是 com.pay.dto.OrderDTO。

A 发送时写入 __TypeId__=com.order.pojo.OrderDTO，但 B 服务 classpath 下根本没这个类 → ClassNotFoundException！

解决方案：自定义类型映射（常用）

🎯 关键点：生产者和消费者两侧都配置相同的 setIdClassMapping，发送侧写 key 字符串，消费侧用 key 映射到本地 Class，完美解耦包名。

3. setCreateMessageIds(true)：消息追踪的神器

效果 说明
自动生成唯一 ID 每条消息头 messageId（如 a1b2c3d4-e5f6-7890-abcd-ef1234567890 UUID）
日志追踪 打日志时把 messageId 带上，跨 producer→Broker→consumer 全链路串起来
幂等去重 消费者可以把 messageId 存入 Redis 去重表，处理过的消息直接跳过，防止重复消费
死信排查 消息进死信队列时，凭 messageId 反查是哪条出的问题

七、常见坑与注意事项

坑 1：只在生产者/消费者一边配 JSON 转换器 ❌

⚠️ 两边必须都配！

  • ✅ 两边都用 Jackson2JsonMessageConverter → 正常收发 JSON
  • ❌ 生产者用 JSON，消费者用默认 Simple → 消费者收到的是乱码 bytes 或抛 MessageConversionException
  • ❌ 生产者默认 JDK，消费者用 JSON → JSON 反序列化 JDK 字节直接报错

坑 2：消费者参数类型与 TypeId 不匹配 ❌

发送对象 TypeId 消费方法参数 结果
HashMap java.util.HashMap Map<String, Object> ✅ 接口兼容，正常
com.order.OrderDTO com.order.OrderDTO com.pay.OrderDTO（包名不同） ❌ ClassNotFoundException
User POJO com.example.User String msg ✅ Spring 会把 JSON 整个当字符串传（不经过 fromMessage 反序列化对象，但可以用）

最安全：跨服务传递尽量用 Map<String,Object>，或两边都依赖同一个公共 DTO jar，或自定义 setIdClassMapping 映射。

坑 3：用 List 接收泛型擦除导致元素是 LinkedHashMap ❓

解决方案：

  1. 用数组代替 List：public void listen(User[] users)，数组类型保留不擦除
  2. 或消费者侧先用 String json 接收，再手动 objectMapper.readValue(json, new TypeReference<List<User>>(){})

坑 4：DTO 没加无参构造函数 ❌

Jackson 反序列化默认需要类有无参构造函数（或用 @AllArgsConstructor 配合 @Builder 再额外加 @NoArgsConstructor）。否则抛 InvalidDefinitionException: Cannot construct instance of ...。

坑 5：日期/时间字段序列化格式不一致 ❌

LocalDateTime 默认序列化成 [2026,8,8,10,30,0] 数组，消费者期望 "2026-08-08 10:30:00" 字符串。

统一方案：公共依赖中配置全局 jackson-datatype-jsr310 + spring.jackson.date-format，保证两端一致。

问题 一句话总结

3. 核心机制要点

机制 作用

包名不一致时 配 setIdClassMapping 自定义逻辑名
messageId 日志追踪 + 幂等去重 + 死信排查

4. 易错点速记

❌ 只单边配转换器 → 消费侧乱码/抛错

❌ POJO 没无参构造 → Jackson 没法实例化

❌ 跨服务包名不同没配 IdClassMapping → ClassNotFoundException

❌ List<User> 泛型擦除 → 元素变 LinkedHashMap，改用 User[] 数组
