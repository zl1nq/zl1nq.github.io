一、问题背景：消息可靠性从何而来

⭐ 一句话理解：消息可靠性 = 消息至少被消费者处理 1 次，不丢、不漏。

1. 典型场景：支付通知

以支付场景为例，支付服务通过 MQ 通知交易服务更新订单状态：

如果 MQ 通知失败，就会出现：

  • 支付服务中支付流水显示支付成功 ✅
  • 交易服务中订单状态却显示未支付 ❌

此时前端查询支付状态（查的是交易服务），会发现「业务订单未支付」，而用户自己明明已经支付成功 → 用户体验不一致，数据出现不一致。

2. 核心诉求

因此，这里我们必须尽可能确保 MQ 消息的可靠性：

🎯 消息应该至少被消费者处理 1 次。

由此引出两个关键问题：

  • 我们该如何确保 MQ 消息的可靠性？
  • 如果真的发送失败，有没有其它的兜底方案？

3. 可靠性保障全景

消息从生产者到消费者，要经历三个环节，每个环节都可能出问题：

环节 可能问题 保障机制
发送者 → MQ 网络中断、MQ 宕机、路由失败 生产者重试 + 生产者确认
MQ 内部 MQ 宕机导致消息丢失 消息持久化
MQ → 消费者 消费者处理异常、处理一半宕机 消费者确认 + 失败重试

💡 本篇聚焦发送者端的可靠性，主要讲解两大机制：生产者重试机制、发送者确认机制。

二、发送者可靠性：两大保障机制

📌 发送者端保障消息可靠性的两道防线：

机制 防线 解决的问题
生产者重试 第一道 网络故障导致连接中断 → 自动重连重发
生产者确认 第二道 消息到达 MQ 后丢失（路由失败、MQ 异常等）→ 回执告知结果

四、生产者确认机制：投递结果回执

🎯 场景：一般情况下，只要生产者与 MQ 之间的网络连接顺畅，基本不会出现发送消息丢失的情况。但在少数情况下，也会出现消息到达 MQ 之后丢失的现象。

1. 消息丢失的几种情况

丢失环节 具体原因
MQ 内部异常 MQ 内部处理消息的进程发生了异常
未找到 Exchange 生产者发送消息到达 MQ 后，未找到 Exchange
未找到 Queue 消息到达 Exchange 后，未找到合适的 Queue，无法路由

2. 两种确认机制

针对上述情况，RabbitMQ 提供了生产者消息确认机制，包括 Publisher Confirm 和 Publisher Return 两种。在开启确认机制的情况下，当生产者发送消息给 MQ 后，MQ 会根据消息处理的情况返回不同的回执。

机制 中文名 作用范围 触发时机
Publisher Confirm 投递确认 生产者 → MQ Broker 消息是否成功送达 MQ（含入队 / 持久化）
Publisher Return 路由回退 Exchange → Queue 消息到达 Exchange 但无法路由到任何队列

💡 二者关系：Confirm 关注「消息到没到 MQ」，Return 关注「消息是否路由到队列」。Return 触发时，Confirm 仍会返回 ACK（因为消息确实到了 Exchange）。

3. MQ 回执规则总结

在开启确认机制后，MQ 会根据消息处理的情况返回不同的回执：

场景 Confirm 回执 Return 回执
消息到达 MQ，但路由失败 ✅ ACK（投递到交换机成功） ⚠️ 触发（返回路由失败信息）
临时消息投递到 MQ，入队成功 ✅ ACK 不触发
持久消息投递到 MQ，入队完成持久化 ✅ ACK 不触发
其它情况（MQ 异常、找不到 Exchange 等） ❌ NACK 不触发

🧠 速记：路由失败 = ACK + Return；入队成功 = ACK；其它异常 = NACK。

5. 定义 ReturnCallback

📌 ReturnCallback 的作用：当消息发送到交换机时，如果交换机无法将消息路由到任何队列（例如路由键不匹配或队列不存在），RabbitMQ 会返回一个 Return 消息，ReturnCallback 就是用来处理这种场景的。

触发时机：当消息已经到达交换机，但在交换机到队列之间路由失败时，MQ 会返回路由失败回执，RabbitTemplate 收到后就会触发 ReturnCallback；如果正常到达队列，就不会触发。

💡 每个 RabbitTemplate 只能配置一个 ReturnCallback，因此我们可以在配置类中统一设置。

6. 定义 ConfirmCallback

📌 ConfirmCallback 的作用：每条消息发送后，通过回执确认是否成功送达 MQ。

由于每个消息发送时的处理逻辑不一定相同（比如失败后要记录哪条消息、重发到哪里），因此 ConfirmCallback 需要在每次发消息时单独定义。具体来说，是在调用 RabbitTemplate 中的 convertAndSend 方法时，多传递一个参数，也就是 CorrelationData。

CorrelationData 是什么？

CorrelationData 是一个用于关联消息和确认回调的类，其中包含两个核心的东西：

组成部分 作用
id 消息的唯一标识，MQ 对不同消息的回执以此做判断，避免混淆
SettableListenableFuture 回执结果的 Future 对象，将来 MQ 的回执就会通过这个 Future 来返回

💡 我们可以提前给 CorrelationData 中的 Future 添加回调函数来处理消息回执，根据这个标识符判断消息是否成功送达队列。每条消息都传入一个 CorrelationData 对象，然后给这个 data 对象中的 Future 对象添加回调函数即可。

5. 易错点提醒

❌ 重试机制是阻塞式的，性能敏感场景慎用，或用异步线程发送消息。

❌ ReturnCallback 触发时，ConfirmCallback 仍会返回 ACK（消息确实到了交换机）。

❌ ReturnCallback 每个 RabbitTemplate 只能配一个，必须全局统一设置；ConfirmCallback 要每条消息单独定义。

❌ publisher-confirm-type 推荐用 correlated（异步），simple 会阻塞业务线程。
