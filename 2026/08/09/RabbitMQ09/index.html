一、消费者确认机制

⭐ 当 RabbitMQ 向消费者投递消息以后，需要知道消费者的处理状态。因为消息投递给消费者并不代表就一定被正确消费了。

可能出现的故障有很多：

  • 消息投递的过程中出现了网络故障
  • 消费者接收到消息后突然宕机
  • 消费者接收到消息后，因处理不当导致异常

一旦发生上述情况，消息也会丢失。因此，RabbitMQ 必须知道消费者的处理状态，一旦消息处理失败才能重新投递消息。

1. 三种回执

为了确认消费者是否成功处理消息，RabbitMQ 提供了消费者确认机制（Consumer Acknowledgement）：当消费者处理消息结束后，应该向 RabbitMQ 发送一个回执，告知 RabbitMQ 自己消息处理状态。回执有三种可选值：

回执 含义 RabbitMQ 动作
ack 成功处理消息 从队列中删除该消息
nack 消息处理失败 再次投递消息（重新入队）
reject 消息处理失败并拒绝 从队列中删除该消息

💡 一般 reject 方式用的较少，除非是消息格式有问题（那就是开发问题了）。因此大多数情况下我们需要将消息处理的代码通过 try-catch 机制捕获，消息处理成功时返回 ack，处理失败时返回 nack。

2. SpringAMQP 的三种 ACK 模式

由于消息回执的处理代码比较统一，因此 SpringAMQP 帮我们实现了消息确认，并允许我们通过配置文件设置 ACK 处理方式，有三种模式：

模式 说明 安全性
none 不处理。消息投递给消费者后立刻 ack，消息会立刻从 MQ 删除 ❌ 非常不安全，不建议使用
manual 手动模式。需要自己在业务代码中调用 api，发送 ack 或 reject ✅ 更灵活，但存在业务入侵
auto 自动模式。SpringAMQP 利用 AOP 对消息处理逻辑做环绕增强 ✅ 推荐

auto 模式的自动判断逻辑：

  • 业务正常执行 → 自动返回 ack
  • 业务出现异常时，根据异常类型判断：
    • 业务异常（如 RuntimeException）→ 自动返回 nack（消息重新入队）
    • 消息处理 / 校验异常 → 自动返回 reject（消息被删除）

返回 reject 的常见异常有：

异常 说明
MessageConversionException 消息转换异常，比如消息格式错误
MethodArgumentNotValidException 方法参数校验异常，比如用户名为空、密码为空等

二、消费者重试机制

1. 问题：无限 requeue 死循环

当消费者出现异常后，消息会不断 requeue（重入队）到队列，再重新发送给消费者。如果消费者再次执行依然出错，消息会再次 requeue 到队列，再次投递，直到消息处理成功为止。

❌ 极端情况就是消费者一直无法执行成功，那么消息 requeue 就会无限循环，导致 MQ 的消息处理飙升，带来不必要的压力。

2. 解决方案：本地重试

为了应对上述情况，Spring 又提供了消费者失败重试机制：在消费者出现异常时利用本地重试，而不是无限制的 requeue 到 MQ 队列。

✅ 结论：

  • 开启本地重试时，消息处理过程中抛出异常，不会 requeue 到队列，而是在消费者本地重试
  • 重试达到最大次数后，Spring 会返回 reject，消息会被丢弃

三、失败处理策略

1. 三种 MessageRecovery 策略

在之前的测试中，本地重试达到最大次数后，消息会被丢弃。这在某些对于消息可靠性要求较高的业务场景下，显然不太合适。

因此 Spring 允许我们自定义重试次数耗尽后的消息处理策略，这个策略是由 MessageRecovery 接口来定义的，它有 3 个不同实现：

策略 行为 是否默认
RejectAndDontRequeueRecoverer 重试耗尽后，直接 reject，丢弃消息 ✅ 默认
ImmediateRequeueMessageRecoverer 重试耗尽后，返回 nack，消息重新入队
RepublishMessageRecoverer 重试耗尽后，将失败消息投递到指定的交换机

2. 推荐：RepublishMessageRecoverer

比较优雅的一种处理方案是 RepublishMessageRecoverer：失败后将消息投递到一个专门的、存放异常消息的队列，后续由人工集中处理。

四、业务幂等性

1. 什么是幂等性

🧠 幂等是一个数学概念，用函数表达式来描述是：f(f(x)) = f(x)，例如求绝对值函数。

在程序开发中，则是指同一个业务，执行一次或多次对业务状态的影响是一致的。

幂等操作示例：

操作 为什么幂等
根据 id 删除数据 第二次删除影响 0 行，结果一致
查询数据 只读操作，不改变状态
设置字段为固定值（如 status = 'paid'） 多次设置结果相同

⚠️ 注意：新增数据不是幂等的，重复新增会产生多条记录。

非幂等操作示例：

操作 为什么不幂等
取消订单、恢复库存 多次恢复会导致库存重复增加
退款业务 重复退款对商家有经济损失
数值加减（如 count = count + 1） 每次执行结果都不同

2. 为什么消息会重复

所以，我们要尽可能避免业务被重复执行。然而在实际业务场景中，由于意外经常会出现业务被重复执行的情况，例如：

  • 页面卡顿时频繁刷新导致表单重复提交
  • 服务间调用的重试
  • MQ 消息的重复投递

3. 两种保障方案

要保证消息处理的幂等性，需要在业务中添加一些额外的逻辑：

方案 思路 特点
唯一消息 ID 给每条消息生成唯一 ID，消费后记录，重复消息放弃处理 通用、与业务解耦
业务状态判断 基于业务本身的状态判断是否已处理 无需改造数据库，但依赖业务字段

方案一：唯一消息 ID

思路非常简单：

  1. 每一条消息都生成一个唯一的 id，与消息一起投递给消费者
  2. 消费者接收到消息后处理自己的业务，业务处理成功后将消息 ID 保存到数据库
  3. 如果下次又收到相同消息，去数据库查询判断是否存在，存在则为重复消息放弃处理

💡 如何给消息添加唯一 ID？SpringAMQP 的 MessageConverter 自带了 MessageID 功能，我们只要开启这个功能即可。

方案二：业务状态判断

业务判断就是基于业务本身的逻辑或状态来判断是否是重复的请求或消息，不同的业务场景判断的思路也不一样。

举例：

  1. 假如用户刚刚支付完成，并且投递消息到交易服务，交易服务更改订单为已支付状态
  2. 由于某种原因（例如网络故障导致生产者没有得到确认），隔了一段时间后重新投递给交易服务
  3. 但是，在新投递的消息被消费之前，用户选择了退款，将订单状态改为了已退款状态
  4. 退款完成后，新投递的消息才被消费，那么订单状态会被再次改为已支付 → 业务异常

💡 当前案例中，处理消息的业务逻辑是把订单状态从「未支付」修改为「已支付」。因此我们就可以在执行业务时判断订单状态是否是未支付，如果不是则证明订单已经被处理过，无需重复处理。

4. 两种方案对比

维度 唯一消息 ID 业务状态判断
通用性 ✅ 通用，与业务解耦 ❌ 依赖具体业务字段
数据库改造 需加一张消息记录表 无需改造
适用场景 无合适业务状态字段（如数值加减）、逻辑复杂 有明确状态字段可判断

🧠 唯一消息 ID 方案有其不可替代的价值：在某些业务场景下可能没有合适的业务状态字段用来判断（如数值加减），或者逻辑极其复杂，此时一个通用的、与业务解耦的「消息记录表」方案会是更好的选择。所谓「改造数据库」通常只是加一张 message_log 表，成本并不高。

五、兜底方案

⭐ 虽然有各种机制可以增加消息的可靠性，但是最终还是会有消息丢失的风险。

1. 思路：主动查询

在订单支付场景下，兜底方案的思路很简单：既然 MQ 通知如果失败，那么交易服务就必须自己主动去查询支付状态。这样即便支付服务的 MQ 通知失败，我们依然能通过主动查询来保证订单状态的一致性。

2. 定时任务查询

不过需要注意的是，交易服务并不知道用户会在什么时候支付，如果查询的时机不正确（比如查询的时候用户正在支付中），可能查询到的支付状态也不正确。

💡 这个时间是无法确定的，因此通常我们采取的措施就是利用定时任务定期查询，例如每隔 20 秒就查询一次，并判断支付状态。如果发现订单已经支付，则立刻更新订单状态为已支付即可。

六、总结与速记

1. 消费者可靠性核心知识点

维度 说明
消费者确认 ack / nack / reject 三种回执
推荐 ACK 模式 auto（业务异常→nack，转换/校验异常→reject）
消费者重试 本地重试，避免无限 requeue 死循环
失败处理策略 RepublishMessageRecoverer 投递到错误队列（推荐）
业务幂等性 唯一消息 ID + 业务状态判断
兜底方案 定时任务主动查询支付状态

5. 易错点提醒

❌ none 模式下消息投递后立刻 ack，异常也不会重新投递，非常不安全。

❌ 开启本地重试后，异常不会 requeue 到 MQ，而是在本地重试；耗尽后返回 reject 丢弃消息。
